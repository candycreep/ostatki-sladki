# Матрица прослеживаемости

Связывает требования из [requirements.md](./requirements.md) с решениями, кодом и проверками. Обновляется **в том же запросе на слияние**, в котором меняется требование, решение или тест. Полнота матрицы проверяется на защите проекта (ЛР 9Б).

**Состояния**: `Записано` → `Спроектировано` → `Реализовано` → `Проверено`

**Контекст** в колонке «Источник» — ограниченный контекст из [модели предметной области](./domain/event-storming.md#ограниченные-контексты): каждое функциональное требование принадлежит ровно одному.

**Что входит**: требования категорий `Must` и `Should` — их берут в работу. `Could` и `Won't` попадают сюда, когда их берут в спринт: до этого решения, кода и проверки у них нет, а пустые строки мешают видеть настоящие пропуски.

## Обратная проверка: шаг пути покупателя без требования

Путь — главный сценарий из [requirements.md, «Путь клиента»](./requirements.md#путь-клиента), плюс действия пекарни из персон.

| Шаг пути (ЛР 1А) | Из какого требования следует |
| --- | --- |
| 2. Открывает сайт, указывает адрес | `FR-02`, `AC-02.4` |
| 2. …в следующий раз адрес запомнен | **Требования не было** → добавлен `AC-02.7` в `FR-02` |
| 2. …в v1.1 узнаёт о новых остатках из MAX | `FR-09` |
| 3. Видит предложения рядом | `FR-02`, `AC-02.1`…`AC-02.3` |
| 4. Открывает карточку и бронирует | `FR-02` (`AC-02.6`), `FR-03`, `NFR-02` |
| 5. Получает код выдачи, видит его в «моих бронях» | `FR-03`, `AC-03.1` |
| 5. …может отменить | `FR-06` |
| 6. Приходит и называет код | `FR-05` |
| 7. Получает набор, платит на месте | `FR-05`; оплата — не требование, а ограничение `C-08` |
| Администратор: выставляет остатки | `FR-01` |
| Администратор: собирает наборы к окну | `FR-04` |
| Продавец: понимает, что бронь «сгорела» и набор свободен | `FR-07`, `AC-04.5` |

Найден один шаг без требования — запоминание адреса; закрыт критерием `AC-02.7`, а не отдельным требованием: это часть того же действия «найти предложения рядом».

## Как обновлять

- Новое требование — новая строка в том же запросе на слияние, что и изменение `requirements.md`
- Колонка «Решение» заполняется номерами записей о решениях (ЛР 2В), «Код» — модулями (с ЛР 3), «Проверка» — тестами (с ЛР 3Б и ЛР 5)
- Состояние меняется только вместе с тем, что его подтверждает: «Реализовано» — с кодом в `develop`, «Проверено» — с зелёным тестом
- Механическая проверка в конвейере (задание `requirements`): строка таблицы без идентификатора требования и требование к качеству без числа делают конвейер красным
