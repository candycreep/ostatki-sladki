# Агрегаты

> Черновик по требованиям ЛР 2А, сверяется с итогами сессии моделирования событий ([event-storming.md](./event-storming.md)). Имена в коде — из [ubiquitous-language.md](./ubiquitous-language.md).

Три агрегата: два в основном контексте «Бронирование и выдача» — `Offer` и `Booking`, один в поддерживающем контексте «Пекарни» — `Bakery`.

## Предложение (Offer)

**Корень**: `Offer`
**Контекст**: Бронирование и выдача

### Состав

| Элемент | Вид | Почему так |
| --- | --- | --- |
| `Offer` | Сущность, корень | Имеет тождество: «какое именно предложение» — осмысленный вопрос, на него ссылаются брони |
| `BundleDescription` | Значение | Название и состав набора. Два одинаковых описания — одно и то же описание |
| `Price` | Значение | Обычная и сниженная цена в копейках; неизменяемы — новая цена означает новое значение |
| `PickupWindow` | Значение | Полуоткрытый интервал `[начало, конец)` с часовым поясом точки выдачи. «Какое именно окно 19:00–20:30» — вопрос без смысла |
| `BundleCount` | Значение | Количество наборов: целое от 1 до 50 |
| `remaining` | Значение (целое) | Остаток — сколько наборов ещё можно забронировать |
| `PickupLocation` | Значение | Идентификатор точки выдачи и её координаты на момент публикации — снимок из контекста «Пекарни» |
| `OfferStatus` | Значение (перечисление) | `active` / `withdrawn` (снято пекарней, `FR-10`, v1.1). «Закончилось» не хранится: следует из окна и текущего времени |

### Инварианты

| № | Инвариант | Почему инвариант, а не правило сценария |
| --- | --- | --- |
| И-1 | `0 ≤ remaining ≤ количество` | Проверяется по данным самого агрегата |
| И-2 | Сниженная цена больше нуля и меньше обычной | По данным агрегата |
| И-3 | Окно: конец позже начала, длительность от 15 минут до 4 часов, начало и конец — в одних сутках по часовому поясу точки | По данным агрегата (`AC-01.3`, `AC-01.4`) |
| И-4 | Резервирование `n` наборов уменьшает остаток ровно на `n` и возможно только при `n ≤ remaining`; возврат `n` наборов увеличивает остаток на `n`, не выше количества | По данным агрегата; защищает `NFR-04` |
| И-5 | Количество нельзя уменьшить ниже числа уже забронированных наборов (`количество − remaining`) | По данным агрегата (`AC-10.2`) |

### Что инвариантом не является

| Правило | Почему не инвариант | Где проверяется |
| --- | --- | --- |
| Приём броней открыт: до конца окна больше 15 минут | Нужно текущее время — внешняя зависимость | Сценарий брони, часы из `ports/` (`AC-03.5`) |
| Окно не заканчивается в прошлом | То же | Сценарий публикации (`AC-01.5`) |
| Публикует сотрудник этой пекарни | Нужен контекст «Доступ» | Сценарий: проверка прав по идентификатору (`NFR-02`) |

### События

| Событие | Когда | Что несёт |
| --- | --- | --- |
| `OfferPublished` | Предложение опубликовано | `offer_id`, `bakery_id`, описание, цены, окно, количество |
| `BundlesSoldOut` | Остаток стал 0 | `offer_id` |
| `BundlesReturned` | Остаток вернулся после отмены | `offer_id`, сколько вернулось, новый остаток |
| `OfferWithdrawn` | Снято пекарней (v1.1) | `offer_id`, кто снял |

Резервирование наборов отдельным событием не публикуется: оно всегда часть `BookingCreated`.

## Бронь (Booking)

**Корень**: `Booking`
**Контекст**: Бронирование и выдача

### Состав

| Элемент | Вид | Почему так |
| --- | --- | --- |
| `Booking` | Сущность, корень | Имеет тождество; на неё ссылаются «мои брони» покупателя и список дня пекарни |
| `PickupCode` | Значение | Шесть знаков из 31 допустимого (`NFR-03`); строчные приводятся к заглавным |
| `BundleCount` | Значение | От 1 до 3 наборов в одной брони |
| `PickupWindow` | Значение | Копия окна предложения на момент брони: состояние брони и правила отмены и выдачи проверяются без загрузки предложения |
| `BookingStatus` | Значение (перечисление) | `created` / `issued` / `cancelled_by_buyer` / `cancelled_by_bakery` (v1.1). «Не забрана» (`not_collected`) не хранится, а читается из `created` и конца окна (вход для `ADR-0005`). Читаемых состояний пять, хранимых четыре |
| `Issue` | Значение | Момент выдачи и кто выдал |
| `Cancellation` | Значение | Момент, кто отменил, причина — обязательна при отмене пекарней (`AC-14.4`) |

### Инварианты

| № | Инвариант | Почему инвариант, а не правило сценария |
| --- | --- | --- |
| И-6 | В брони от 1 до 3 наборов | По данным агрегата (`AC-03.4`) |
| И-7 | Переходы только из `created`; «выдана», «отменена» и «не забрана» — конечные | По состоянию агрегата |
| И-8 | Выдача — только при `начало ≤ сейчас < конец` окна | По данным агрегата и переданному моменту времени (`AC-05.4`) |
| И-9 | Отмена покупателем — только при `сейчас < начало` окна | То же (`AC-06.2`) |
| И-10 | При `сейчас ≥ конец` окна бронь в `created` читается как «не забрана», и никакой переход из неё невозможен | То же (`AC-07.4`, `AC-07.5`) |
| И-11 | У выданной брони есть момент выдачи и сотрудник; у отменённой — момент отмены | По данным агрегата |

Время передаётся в агрегат как значение из сценария: сам агрегат часов не читает. Поэтому И-8…И-10 — инварианты относительно переданного момента, и проверяются тестами без ожидания (`AC-07.4` в [traceability.md](../traceability.md)).

### Что инвариантом не является

| Правило | Почему не инвариант | Где проверяется |
| --- | --- | --- |
| Остаток достаточен | Нужен агрегат `Offer` | Сценарий брони: резервирование в `Offer` (И-4) |
| Одна бронь в `created` на покупателя и предложение | Нужны другие брони — другие экземпляры агрегата | Сценарий брони с обращением к хранилищу; от состязания двух запросов защищает база (ЛР 4А) |
| Код уникален среди активных броней пекарни | Нужны другие брони | Сценарий: порождение кода с повтором при совпадении; уникальность в базе (ЛР 4А) |
| Выдачу отмечает сотрудник этой пекарни | Нужен контекст «Доступ» | Сценарий: проверка прав (`NFR-02`) |
| Покупатель не на паузе после трёх неявок | Нужна история броней покупателя | Сценарий брони, v1.1 (`FR-13`) |

### События

| Событие | Когда | Что несёт |
| --- | --- | --- |
| `BookingCreated` | Бронь создана | `booking_id`, `offer_id`, `bakery_id`, `buyer_id`, число наборов, конец окна |
| `BookingIssued` | Набор выдан | `booking_id`, момент, `staff_id` |
| `BookingCancelled` | Отменена покупателем | `booking_id`, момент, сколько наборов вернулось |
| `BookingCancelledByBakery` | Отменена пекарней (v1.1) | `booking_id`, причина, `staff_id` |
| `BookingNotCollected` | Окно закончилось без выдачи | `booking_id`. **Вызывается временем, не командой**; без срабатывания по расписанию публикуется с задержкой — см. `ADR-0005` |

Код выдачи в события не входит: его не должен видеть никто, кроме покупателя и пекарни (`NFR-05`).

### Почему бронь и предложение — два агрегата, хотя бронь меняет остаток

Создание брони меняет два агрегата: резервирует наборы в `Offer` и создаёт `Booking`. Правило «одна транзакция — один агрегат» здесь нарушено сознательно.

| Вариант | За | Против |
| --- | --- | --- |
| **Два агрегата, изменение обоих в одной транзакции сценария** | Бронь живёт отдельно: «мои брони», поиск по коду, выдача не загружают предложение целиком. Инвариант остатка (И-1, И-4) — внутри `Offer` | Нарушено «одна транзакция — один агрегат»; оба агрегата обязаны лежать в одной базе |
| Брони внутри агрегата `Offer` | Одна граница согласованности: правило «не продать больше» — чистый инвариант | Каждая выдача и отмена загружает предложение со всеми бронями; на бронь нельзя сослаться отдельно; два покупателя одного предложения мешают друг другу на любой операции, а не только на брони |
| Два агрегата, остаток уменьшается позже, по событию | Каждая транзакция меняет один агрегат | Между созданием брони и уменьшением остатка можно продать лишнее — нарушает `NFR-04` |

Довод — `NFR-04`: перепродажа недопустима, а третий вариант её допускает. Между первыми двумя выбран первый: при 1–20 бронях на предложение совместное изменение двух агрегатов в одной транзакции дешевле, чем агрегат, который приходится загружать целиком на каждую выдачу. Цена — оба агрегата в одной базе; это вход для записи о стиле `ADR-0003`.

## Пекарня (Bakery)

**Корень**: `Bakery`
**Контекст**: Пекарни

### Состав

| Элемент | Вид | Почему так |
| --- | --- | --- |
| `Bakery` | Сущность, корень | Имеет тождество |
| `PickupPoint` | Сущность внутри агрегата | Имеет тождество внутри пекарни — на неё ссылается предложение, — но без пекарни не существует |
| `Address` | Значение | Адрес точки выдачи текстом |
| `Location` | Значение | Широта и долгота; два одинаковых — одно и то же место |
| `StaffMember` | Сущность внутри агрегата | Учётная запись сотрудника и роль в этой пекарне |
| `StaffRole` | Значение (перечисление) | `admin` / `seller` |

### Инварианты

| № | Инвариант |
| --- | --- |
| И-12 | Ровно одна точка выдачи (`C-11`) |
| И-13 | У точки выдачи есть координаты: пекарня без определённых координат в поиске не участвует и предложения не публикует |
| И-14 | В пекарне есть хотя бы один администратор |
| И-15 | Сотрудник в пекарне не повторяется |

### События

| Событие | Что несёт |
| --- | --- |
| `BakeryRegistered` | `bakery_id`, название |
| `PickupPointLocated` | `bakery_id`, `pickup_point_id`, координаты |
| `StaffMemberAdded` | `bakery_id`, учётная запись, роль |

### Границы

Контекст «Пекарни» не знает о предложениях и бронях. Бронирование ссылается на пекарню и точку выдачи по идентификатору, а координаты получает снимком при публикации (`PickupLocation` в `Offer`): поиск рядом не обращается к другому контексту на каждый запрос.
