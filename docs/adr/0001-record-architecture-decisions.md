# 1. Мы ведём записи об архитектурных решениях

- **Статус**: предложено
- **Дата**: 2026-11-06
- **Участники**: Иванов Дмитрий (запись), Кобелев Владислав (подтверждение в ревью)

## Контекст

Решения ЛР 1 записаны только итогом, без причин: в глоссарии сказано, что код выдачи — шесть символов, в MVP — что оплата на месте, но почему именно так, в документах нет. Причину длины кода пришлось восстанавливать заново, когда записывалось `NFR-03`. Код ещё не написан, а решений, которые дорого менять, впереди много: стиль системы, способ входа, хранение состояния брони.

Нужен способ фиксировать решения так, чтобы к ним можно было вернуться и через месяц, и на защите.

## Движущие факторы

- Решение, причина которого утеряна, обходят вместо того, чтобы менять
- `C-04`: команда из двух человек, участники работают в разное время — решения передаются письменно, а не голосом
- Защита проекта (ЛР 9Б) требует обоснования принятых решений
- Записи должны лежать рядом с кодом: отдельное хранилище документов расходится с системой в первую же неделю

## Рассмотренные варианты

| Вариант | За | Против |
| --- | --- | --- |
| **Записи в репозитории по формату MADR** | Рядом с кодом; проходят ревью в запросе на слияние; история в Git; на запись можно сослаться из кода и из матрицы прослеживаемости | Нужна дисциплина: запись придётся писать, это 20–60 минут |
| Раздел «Решения» в `requirements.md` | Одно место для всего | Решения тонут среди требований; изменение решения переписывает старый текст — история «почему не иначе» теряется |
| Описание в карточке Jira | Решение привязано к задаче | Отрывается от кода; после закрытия карточки его никто не находит |
| Не фиксировать | Ничего не нужно делать | Текущее положение, которое и привело к проблеме |

## Решение

Записи в репозитории, в каталоге `docs/adr/`, по формату **MADR**.

Правила:

1. **Одно решение — один файл.** Имя: `NNNN-kebab-case-title.md`, номер четырёхзначный, по порядку, **не переиспользуется**.
2. **Записи не правят и не удаляют.** Изменилось решение — статус старой меняется на «заменено на ADR-NNNN», пишется новая. Исправление опечатки правкой не считается.
3. **Запись нужна решению, которое затрагивает несколько частей системы, трудно обратимо или влияет на атрибуты качества.** Остальное решается в коде и в ревью.
4. **Обязательные разделы**: статус, дата, участники, контекст, движущие факторы со ссылками на требования, рассмотренные варианты (не меньше двух, у каждого доводы за и против), решение с определяющим доводом, последствия с отрицательной частью и условием пересмотра. Наличие разделов проверяет конвейер (задание `decisions`).
5. **Решение принимает команда.** Запись пишет один участник со статусом «предложено»; второй подтверждает её в ревью запроса на слияние, после чего статус меняется на «принято».
6. **Указатель** [`README.md`](./README.md) обновляется в том же запросе на слияние. Новая запись начинается с формы [`docs/templates/adr.md`](../templates/adr.md).

## Последствия

**Положительные.** Причина решения доступна через месяцы. Спор, разобранный один раз, не повторяется. Защита проекта опирается на записи, а не на память. Колонка «Решение» матрицы прослеживаемости получает адресуемые номера.

**Отрицательные.** Запись стоит времени, а у команды из двух человек его мало. Есть риск формальных записей ради наличия: конвейер проверяет только разделы, не смысл, — смысл проверяется ревью второго участника.

**Что пересмотрит решение.** Появление в вузе единого требования к оформлению проектной документации, несовместимого с этой формой; переход проекта в другую систему хранения кода, где Markdown не отображается.
