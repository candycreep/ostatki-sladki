# 5. Состояние «не забрана» вычисляется при чтении, а не по расписанию

- **Статус**: предложено
- **Дата**: 2026-11-06
- **Участники**: Иванов Дмитрий (запись), Кобелев Владислав (подтверждение в ревью)

## Контекст

`FR-07` требует, чтобы невыданная бронь становилась «не забрана» ровно в момент конца окна выдачи: в 20:29:59 — «создана», в 20:30:00 — «не забрана» (`AC-07.4`), а выдача в 20:30:00,2 отклоняется (`AC-07.5`). На этом состоянии держатся список дня продавца (`AC-04.5`), метрика `BR-02` и в v1.1 пауза после трёх неявок (`FR-13`).

Переход вызывается наступлением времени, а не командой. Чтобы состояние «менялось само», нужен механизм срабатывания по расписанию — а его в системе до ЛР 6А нет, и он сам может отставать или не работать. Это конфликт `К-2` из ЛР 2А.

## Движущие факторы

- `FR-07`, `AC-07.4`, `AC-07.5`: переход точно в момент конца окна, без задержки
- `NFR-06`: брони, окно которых закончилось во время простоя, после запуска сразу «не забрана»
- `C-04`, `NFR-07`: простота — без отдельного процесса до ЛР 6А, тесты без ожидания реального времени
- `BR-02`: метрика считается запросом к базе по тем же правилам, что видит продавец
- `FR-08`: напоминание за 30 минут — тоже событие по времени, но ему нужна **отправка**, а не состояние; **не различает варианты** этого решения: для напоминаний обработчик по расписанию нужен в любом случае (ЛР 6А)

## Рассмотренные варианты

| Вариант | За | Против |
| --- | --- | --- |
| **Вычислять при чтении: хранится `created`, а «не забрана» — это `created` при `сейчас ≥ конец окна`** | Точно в момент конца окна; не зависит от того, работает ли что-то по расписанию; переживает простой (`NFR-06`); проверяется тестом с подставными часами | Правило применяется в двух местах — в агрегате и в запросах на чтение списков и метрик, — и они могут разойтись; события `BookingNotCollected` в момент перехода нет |
| Задача по расписанию в процессе API раз в минуту | Состояние хранится явно; событие публикуется при переходе | Отставание до минуты — нарушает `AC-07.4`; при нескольких экземплярах API задача выполняется несколько раз; выдача в 20:30:30 прошла бы |
| Отдельный обработчик по расписанию (ЛР 6А) | Не нагружает API; общий механизм с напоминаниями | До ЛР 6А его нет — `FR-07` из MVP не выполняется; если обработчик остановлен, брони навсегда «создана» |
| Задание по расписанию в базе (`pg_cron`) | Близко к данным, без нового процесса | Расширение базы, которого нет в стандартном образе (`C-05`, `NFR-07`); правило предметной области уходит в SQL — его не проверить тестом предметной логики |

## Решение

**Хранится только состояние, вызванное командой**: `created`, `issued`, `cancelled_by_buyer`, `cancelled_by_bakery`. Состояние «не забрана» (`not_collected`) **вычисляется** при каждом чтении: бронь в `created`, у которой `сейчас ≥ конец окна`, читается и обрабатывается как «не забрана». Агрегат `Booking` получает момент времени из сценария (часы — порт в `ports/`), поэтому И-10 проверяется без ожидания.

Одно правило — одно определение: в коде предметной области это метод брони, в запросах списков и метрик — одно и то же условие `status = 'created' AND window_ends_at <= now()`, вынесенное в общее представление базы (ЛР 4А). Расхождение двух мест ловит тест, сравнивающий их на одних данных.

**Определяющий довод** — `AC-07.4` вместе с `NFR-06`. Только вычисление при чтении даёт переход ровно в момент конца окна и правильное состояние после простоя; любое расписание даёт задержку и зависит от того, работает ли оно.

## Итог

**Положительные.** `FR-07` выполняется уже в MVP, без нового процесса. Состояние всегда согласовано со временем, в том числе после перезапуска. Тесты — с подставными часами, без ожидания.

**Отрицательные.** **События `BookingNotCollected` в момент перехода нет**: ничего не «происходит» в 20:30. Потребители, которым нужен факт неявки, — пауза после трёх неявок (`FR-13`) и итоги (`FR-11`), — в v1.1 либо считают его запросом, либо получают событие от обработчика по расписанию с задержкой. Это записанный долг, он разбирается в ЛР 9Б. Правило живёт в двух местах — в агрегате и в представлении базы, — их нужно держать согласованными. Хранимое `created` у давно закончившейся брони может сбить с толку при чтении базы напрямую.

**Что пересмотрит решение.** Требование уведомлять кого-то в момент неявки (например, лист ожидания или сообщение пекарне); появление обработчика по расписанию, отставание которого измерено и укладывается в требования; рост числа броней, при котором вычисление в каждом запросе станет заметным по `NFR-01`.
