# 3. Модульный монолит с гексагональным устройством

- **Статус**: предложено
- **Дата**: 2026-11-06
- **Участники**: Иванов Дмитрий (запись), Кобелев Владислав (подтверждение в ревью)

## Контекст

Нужно решить, как система организована в целом: одно приложение или несколько служб, и как устроено внутри. Решение определяет развёртывание, тестирование, устройство кода и объём эксплуатации.

Что известно к моменту решения. Модель предметной области (ЛР 2Б) выделяет основной контекст «Бронирование и выдача» и поддерживающие «Пекарни», «Доступ», «Уведомления», «Итоги». Создание брони меняет два агрегата — `Offer` и `Booking` — в одной транзакции, иначе возможна перепродажа ([aggregates.md](../domain/aggregates.md)). В системе будут сервис API и база данных (ЛР 3, 4), обработчик событий для уведомлений в MAX (ЛР 6А) и браузерное приложение (ЛР 8).

## Движущие факторы

- `C-04`: команда из двух человек, один семестр
- `NFR-04`: наборы не продаются дважды — резервирование в `Offer` и создание `Booking` должны быть согласованы немедленно, то есть лежать в одной базе и меняться в одной транзакции
- `NFR-07`: прогон тестов не дольше 60 секунд, установка — не больше 5 команд
- `C-05`: развёртывание через Compose, оркестрация не применяется
- `C-10`: асинхронный сценарий через брокер — уведомления обрабатываются отдельно от запроса
- Предложение о структуре кода из ЛР 2Б: контексты — модули внутри `domain/`
- `NFR-01`: 300 мс при 10 запросах в секунду — **не различает варианты**: нагрузка мала для любого из них

## Рассмотренные варианты

| Вариант | За | Против |
| --- | --- | --- |
| **Модульный монолит, внутри гексагональное устройство** | Одно развёртывание; бронь и остаток согласованы в одной транзакции; предметная логика проверяется без базы и сети; границы контекстов готовят возможное разделение | Границы держатся договорённостью и проверкой в конвейере, а не техническим барьером: их можно нарушить одним импортом |
| Монолит без явных границ | Меньше файлов и уровней; быстрее начать | Через два месяца контексты сливаются; правила брони перестают проверяться без базы — тесты медленнее, `NFR-07` под угрозой |
| Микросервисы: каталог и пекарни, брони, уведомления | Независимые выпуски и масштабирование | Остаток и брони в разных базах — для `NFR-04` нужна распределённая согласованность; три конвейера и три набора наблюдаемости на двоих — при `C-04` неисполнимо |
| Монолит плюс бессерверные функции для уведомлений | Уведомления масштабируются сами | Внешняя платформа — против `C-06` и `C-05`; локальная разработка и тесты `AC-08.4` усложняются |

## Решение

**Модульный монолит с гексагональным устройством внутри.** Одно приложение, одна база данных PostgreSQL (`C-02`), явные границы между предметной областью, интерфейсами и адаптерами. Обработчик событий (ЛР 6А) — отдельный процесс **того же** приложения и той же базы: это разделение по способу запуска, а не по данным, и микросервисной систему не делает.

**Определяющий довод** — `NFR-04` вместе с `C-04`. Правило «не продать больше, чем есть» требует, чтобы остаток и брони менялись в одной транзакции; в монолите с одной базой это даётся бесплатно, а в любом распределённом варианте стоит больше, чем вся остальная система. Независимость служб при команде из двух человек ничего не даёт: выпускать независимо нечего и некому.

Устройство кода:

- `src/ostatki/domain/booking/` — агрегаты `Offer` и `Booking`; `src/ostatki/domain/bakeries/` — агрегат `Bakery`;
- `src/ostatki/ports/` — интерфейсы хранилищ, часов, службы координат, отправки уведомлений; `src/ostatki/adapters/` — их реализации; `src/ostatki/services/` — сценарии;
- обмен между контекстами — по идентификатору и значениям: `domain/booking` не импортирует `domain/bakeries`.

Границы проверяются конвейером с появлением кода (ЛР 3Б, задание `boundaries`). Обе команды должны давать пустой результат:

```bash
grep -rnE "fastapi|sqlalchemy|asyncpg|httpx|aio_pika" src/ostatki/domain
grep -rn "domain.bakeries" src/ostatki/domain/booking
```

## Последствия

**Положительные.** Одно развёртывание, одна база, согласованность брони и остатка в транзакции (`NFR-04`). Правила брони проверяются без внешних средств — тесты остаются быстрыми (`NFR-07`). Границы контекстов дают путь к разделению, если оно понадобится.

**Отрицательные.** Все части выпускаются вместе: ошибка в уведомлениях останавливает выпуск исправления брони. Масштабирование — только целым приложением. Совместное изменение двух агрегатов в одной транзакции привязывает основной контекст к одной базе навсегда: выделить брони в отдельную службу без переделки модели нельзя. Границы обеспечены проверкой, которую можно обойти или отключить.

**Что пересмотрит решение.** Появление второй команды, работающей над системой независимо; требование разной частоты выпуска для разных частей; нагрузка, при которой уведомления требуют в разы больше ресурсов, чем остальное.
