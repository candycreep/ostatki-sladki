# Архитектурные диаграммы

Все диаграммы — текст в формате Mermaid. GitHub отрисовывает их при просмотре файла. Конвейер проверяет каждую: диаграмма, которая не отрисовывается, не проходит (задание `diagrams`). Обзор системы, решения и тактики — в [overview.md](./overview.md).

## Что здесь есть

| Файл | Что показывает | Для кого | На какой вопрос отвечает |
| --- | --- | --- | --- |
| [`c4/context.mmd`](./c4/context.mmd) | Система одним блоком, четыре действующих лица, четыре внешние системы | Новый человек в проекте, пекарня-заказчик | С чем система граничит и кто ею пользуется? |
| [`c4/container.mmd`](./c4/container.mmd) | Пять контейнеров с технологиями и протоколами, события на связях с брокером | Разработчик, впервые открывший проект; эксплуатация | Из каких запускаемых частей система состоит и на чём они сделаны? |
| [`c4/component-api.mmd`](./c4/component-api.mmd) | Компоненты сервиса API по слоям: входные адаптеры, сценарии, предметная область, порты, выходные адаптеры | Разработчик, который пишет код в ЛР 3А–3Б | Где в сервисе API лежит правило, сценарий или обращение к внешней системе, и что от чего зависит? |
| [`sequence/create-booking.mmd`](./sequence/create-booking.mmd) | Бронь (`FR-03`) по шагам, все ветви отказа | Разработчик сценария брони | В каком порядке что вызывается, когда покупатель бронирует, и где отказ? |
| [`data/model.mmd`](./data/model.mmd) | Сущности, атрибуты, ключи, связи с кардинальностью | Тот, кто пишет первую миграцию в ЛР 4А | Какие таблицы, ключи и связи? |

Перечень операций REST — в [`../api/resources.md`](../api/resources.md): это та же схема взаимодействия клиента и сервиса, что на диаграмме контейнеров, на уровне операций.

## Чего здесь нет и почему

| Чего нет | Почему |
| --- | --- |
| Компоненты обработчика событий | Тот же код, что у сервиса API (`ADR-0003`): те же сценарии и адаптеры, другой только входной адаптер — получатель событий из брокера. Отдельная диаграмма появится в ЛР 6А, если устройство разойдётся |
| Уровень кода C4 | Устаревает быстрее, чем пишется; заменяется чтением кода |
| Диаграмма развёртывания | ЛР 6Б |
| Карта контекстов предметной области | ЛР 2Б, лежит в [`../domain/context-map.mmd`](../domain/context-map.mmd) |
| Диаграмма состояний брони | Уже есть в [`../requirements.md`](../requirements.md#состояния-брони); после `ADR-0005` «не забрана» не хранится, а вычисляется — сама диаграмма от этого не меняется |
| Контексты отдельными контейнерами | Модульный монолит (`ADR-0003`): все контексты — модули сервиса API; обработчик событий — тот же код в другом процессе. Искать «службу бронирования» на диаграмме контейнеров бесполезно |

## Как обновлять

Диаграмма правится **в том же запросе на слияние**, который меняет систему. Правило проверяется на ревью: изменение, добавляющее службу в `compose.yaml` без правки `c4/container.mmd`, новый каталог в `src/ostatki/` без правки `c4/component-api.mmd` или миграция без правки `data/model.mmd` не принимаются.

Подписи на стрелках — короткие, одна-две строки. Длинные подписи на связях, пересекающих границу системы, в просмотрщике GitHub налезают друг на друга; подробности — в таблице рядом с диаграммой.

Локальная проверка перед коммитом (нужен Node.js 22):

    npx --yes @mermaid-js/mermaid-cli@11.4.0 -i docs/architecture/c4/context.mmd -o /tmp/out.svg

## Соглашение об оформлении C4

C4 рисуется через `flowchart`, потому что встроенная поддержка `C4Context` в Mermaid неустойчива между версиями. Классы стилей:

| Класс | Что обозначает | Цвет |
| --- | --- | --- |
| `actor` | Человек или роль | голубой |
| `sys` | Наша система или её часть | оранжевый |
| `store` | Хранилище данных, в том числе брокер | зелёный |
| `ext` | Внешняя система | серый |
| `comp` | Компонент внутри контейнера — только на диаграмме компонентов | жёлтый |

Элемент, которого ещё нет, получает класс по своему виду и пометку в подписи номером работы: `<b>ЛР 6А</b>`. На диаграмме компонентов сплошная стрелка — вызов, пунктирная с подписью «реализуется в» — порт и адаптер, который его реализует. Зависимость в коде направлена **от адаптера к порту**: адаптер импортирует интерфейс из `ports/`, а сценарии и предметная область об адаптерах не знают. Стрелка нарисована от порта к адаптеру намеренно — со стрелкой к порту раскладчик Mermaid ставит адаптеры в один ряд со сценариями, и диаграмма вытягивается в ширину. Стрелки — только в одну сторону; двусторонний обмен — две стрелки с разными подписями (MAX → сервис API и обработчик событий → MAX).

## Результат сверки

| Сверка | Результат |
| --- | --- |
| Контекст ↔ контейнеры | Расхождений нет: четыре действующих лица и четыре внешние системы есть на обеих диаграммах, новых на диаграмме контейнеров не появилось |
| Контейнеры ↔ последовательность | Расхождений нет: участники — покупатель, браузерное приложение, сервис API, база данных, брокер; все есть на диаграмме контейнеров |
| Последовательность ↔ критерии приёмки | Все критерии `AC-03.1`…`AC-03.9` показаны ветвями. Обратное расхождение: ветвь «код совпал с активной бронью» не следует ни из одного критерия — она из `NFR-03`. Критерий не добавлен: покупатель этой ветви не видит, она проверяется тестом порождения кода (ЛР 3Б) |
| Контейнеры ↔ решения | `api` — `ADR-0002`, `ADR-0003`; `db` — `C-02`; `worker` — `ADR-0003` (отдельный процесс того же приложения) и `C-10`; `broker` — `C-10`. **Технологии брокера (RabbitMQ 4) и браузерного приложения (Vue 3.5) записями не обоснованы**: на диаграмме — план курса; записи появятся в ЛР 6А и ЛР 8, до этого пометки `ЛР 6А` и `ЛР 8` показывают, что элемента ещё нет. Записано долгом Д-2 в [`../tech-debt.md`](../tech-debt.md) |
| Компоненты ↔ контейнеры | Расхождений нет: все связи сервиса API с диаграммы контейнеров есть на диаграмме компонентов и приходят в конкретный компонент — браузерное приложение, MAX и проверка работоспособности в обработчики HTTP, оператор в команды оператора, база, брокер и служба координат из выходных адаптеров. Связь «конвейер развёртывает образ» на диаграмму компонентов не перенесена: это не вызов компонента во время работы |
| Компоненты ↔ решения | Слои и каталоги — из `ADR-0003`. Уточнение: `ADR-0003` не называет каталог входных адаптеров — обработчики HTTP и команды оператора лежат в `adapters/http/` и `adapters/cli/`, рядом с выходными. Проверка маркера без базы — `ADR-0004`; вычисление «не забрана» в хранилище — `ADR-0005`; «единица работы» среди портов — из правила `NFR-04`: `Offer` и `Booking` меняются в одной транзакции |
| Компоненты ↔ ресурсы API | Все операции из `resources.md` приходят в обработчики HTTP; `FR-31` — в команды оператора, у него HTTP-операции нет. У предметной области исходящих стрелок нет: она не знает ни о базе, ни о FastAPI — это и проверяет задание `boundaries` (ЛР 3Б) |
| Модель данных ↔ требования | `BAKERIES`, `PICKUP_POINTS`, `STAFF_MEMBERS` не создавались ни одним требованием — добавлено `FR-31` «заведение пекарни оператором». `REFRESH_TOKENS` — из `NFR-02` и `ADR-0004`; `MAX_LINKS`, `SUBSCRIPTIONS` — из `FR-08`, `FR-09`. Обратно: у `FR-12` (шаблоны) и `FR-15` (шаги цены) сущностей нет — они появятся вместе с требованиями в v1.1 и v1.2; `FR-11` и `FR-13` вычисляются по `BOOKINGS`, своей сущности им не нужно |
| Модель данных ↔ агрегаты | `Offer` → `OFFERS`: окно, цены и снимок координат — колонками. `Booking` → `BOOKINGS`: копия окна из агрегата в таблице не хранится — окно читается из `OFFERS` при загрузке брони. `Bakery` → `BAKERIES`, `PICKUP_POINTS`, `STAFF_MEMBERS`. Несовпадение моделей — ожидаемое, его разрешает реализация хранилища (ЛР 4А) |
| Ресурсы API ↔ требования | У каждого видимого пользователю требования есть операция. `FR-07` и `FR-31` операций не имеют — с объяснением в `resources.md`. Найдено расхождение с `ADR-0004`: открытая операция поиска адреса `GET /v1/places` не была в перечне открытых — перечень дополнен (запись ещё в статусе «предложено») |

## Решения модели данных

| Решение | Почему |
| --- | --- |
| Первичные ключи — `uuid` | Идентификатор порождается приложением; не раскрывает число броней и пекарен; в тестах предсказуем |
| `email` уникален, но не первичный ключ | Почта может смениться; ссылки на учётную запись от этого страдать не должны |
| Брони не удаляются, отмена — смена `status` | Отменённые и невыданные брони нужны для `BR-02`, `FR-11`, `FR-13` |
| Предложения не удаляются, снятие — `status = withdrawn` | На них ссылаются брони; итоги за период считаются по ним |
| Учётные записи не удаляются, отключение — `disabled_at` | На них ссылаются брони и выдачи; удаление стёрло бы, кто выдал набор |
| `status` брони хранит четыре значения из пяти | «Не забрана» вычисляется: `created` и `window_ends_at` в прошлом (`ADR-0005`) |
| `bakery_id` в `BOOKINGS`, хотя он есть через `OFFERS` | Уникальность кода выдачи — среди активных броней пекарни; ограничение в базе строится по колонкам одной таблицы |
| `pickup_latitude`, `pickup_longitude` в `OFFERS` | Снимок координат точки на момент публикации: поиск рядом читает одну таблицу (`NFR-01`) |
| Цены — целые копейки, `int` | Без ошибок округления дробных чисел |
| `price_kopecks` в `BOOKINGS` | Цена фиксируется в момент брони (`FR-15`); до v1.2 равна сниженной цене предложения |
| Ключи повтора `publish_key`, `booking_key` | `AC-01.2`, `AC-03.7`: повтор запроса не создаёт вторую запись |
| `STAFF_MEMBERS` — отдельная сущность с составным ключом | Связь «многие ко многим» учётной записи и пекарни с собственным атрибутом — ролью; составной ключ выражает И-15 «сотрудник не повторяется» |
| Все метки времени — `timestamptz`; часовой пояс точки — отдельной колонкой | «Сегодня» и сутки окна считаются по местному времени точки выдачи |
| Пустые значения — только у моментов, которых ещё не было | `issued_at`, `cancelled_at`, `revoked_at`, `withdrawn_at`, `disabled_at`, `reminder_sent_at` |
