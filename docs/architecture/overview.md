# Обзор архитектуры

Документ для того, кто впервые открыл проект. Даёт картину целиком за десять минут чтения и ссылается на подробности. **Не повторяет** содержание диаграмм и записей о решениях.

## Что это за система

«Остатки сладки» — сервис для небольших пекарен. К концу дня пекарня публикует нераспроданную выпечку наборами со сниженной ценой и окном выдачи; покупатели поблизости видят предложения, бронируют один–три набора, получают код и забирают набор в окно выдачи, оплачивая на месте. Продавец выдаёт по коду; бронь, за которой не пришли, по окончании окна становится «не забрана». Задача — превратить списание в выручку без переписки и звонков (`BR-01`…`BR-03`).

Границы: одна точка выдачи на пекарню, пекарни заводит команда (`C-11`); оплата только на месте (`C-08`); уведомления только через бот в MAX (`C-07`). Онлайн-оплата, доставка, сети пекарен, отзывы, мобильное приложение — вне охвата (`FR-24`…`FR-30`, `C-03`).

## Принятые решения

| № | Решение | Что определило |
| --- | --- | --- |
| 0002 | Python 3.13 и FastAPI | `C-04`, `C-01` |
| 0003 | Модульный монолит, гексагональное устройство | `NFR-04`, `C-04` |
| 0004 | Почта и пароль, маркер доступа 15 минут, обновляющий маркер в базе | `NFR-02` |

## Как достигаются требования к качеству

| Требование | Тактика | Где реализовано | Состояние |
| --- | --- | --- | --- |
| `NFR-01` 95 % ≤ 300 мс | Адрес переводится в координаты отдельным действием, список запрашивается по координатам (`К-1`); координаты точки выдачи хранятся в предложении снимком; индекс по времени окна и координатам | ЛР 3Б (порт службы координат), ЛР 4А (индекс) | Запланировано |
| `NFR-02` Защита операций | Проверка подлинности и прав на сервере; защищённость по умолчанию; чужое отвечает как несуществующее | ADR-0004; ЛР 4Б | Решено, не реализовано |
| `NFR-03` Стойкость кода | Код из 31 знака, порождаемый криптографическим генератором; уникальность среди активных броней пекарни | ЛР 3Б (порождение), ЛР 4А (уникальность в базе) | Решено, не реализовано |
| `NFR-04` Без перепродажи | Резервирование в `Offer` и создание `Booking` в одной транзакции; условное уменьшение остатка; ограничение «остаток не меньше нуля» в базе | ADR-0003; ЛР 4А | Решено, не реализовано |
| `NFR-05` Журнал без персональных данных | Структурный журнал JSON с идентификатором запроса; в журнал пишутся идентификаторы, а не почта, адреса и коды | ЛР 3А | Решено, не реализовано |
| `NFR-06` Восстановление после перезапуска | Хранение в базе; «не забрана» вычисляется при чтении и верна после простоя; проверка готовности | ADR-0005; ЛР 3А, ЛР 4А | Решено, не реализовано |
| `NFR-07` Стоимость изменения | Разделение на предметную область, порты и адаптеры; подставные часы и внешние службы в тестах; порог покрытия в конвейере | ADR-0003; ЛР 3Б; конвейер | Решено, не реализовано |
| `NFR-08` Своевременность напоминаний | Асинхронная отправка через брокер; повтор с нарастающей задержкой в течение 10 минут; ключ напоминания, чтобы повтор не дублировал (`AC-08.5`) | ЛР 6А | Запланировано |
| `NFR-09` Публикация за 60 с | Минимум обязательных полей; значения по умолчанию для окна; шаблоны наборов (`FR-12`) | ЛР 8 (браузерное приложение), v1.1 (`FR-12`) | Запланировано |

Колонка «Состояние» меняется по мере работ; к защите (ЛР 9Б) в ней не должно остаться «решено, не реализовано» без причины.

**Требования без тактик**: на сервере — нет. Проверено при составлении таблицы. Особый случай — `NFR-09`: его тактики целиком в браузерном приложении и в `FR-12`; до ЛР 8 серверная часть на него не влияет, и это записано, а не пропущено.

## Защищённость

### Принципы

| Принцип | Как применяется |
| --- | --- |
| Наименьшие права | Продавец выдаёт и видит брони, но не публикует и не снимает предложения (`NFR-02`). Процесс в контейнере не от `root` (ЛР 3А). Пользователь базы без права менять схему (ЛР 4А) |
| Защищённость по умолчанию | Обработчик требует маркер, если не включён в явный перечень открытых: список рядом, карточка, вход, регистрация, проверка работоспособности (ADR-0004) |
| Эшелонированная защита | Остаток защищён трижды: инвариант `Offer` (И-1), условное уменьшение в сценарии, ограничение в базе |
| Безопасный отказ | Ошибка проверки маркера — отказ в доступе. Сбой отправки в MAX бронь не меняет (`AC-08.4`) |
| Минимум поверхности | Порт базы и брокера наружу не публикуется; описание API закрыто вне разработки; код выдачи не попадает ни в журнал, ни в события |

### Модель угроз: введение

| Угроза | Как может проявиться | Защита | Состояние |
| --- | --- | --- | --- |
| Подмена личности | Вход от имени другого покупателя; сотрудник одной пекарни выдаёт по брони другой | Подписанный маркер с пекарней сотрудника (ADR-0004); поиск кода только в своей пекарне (`AC-05.7`) | ЛР 4Б |
| Искажение данных | Изменение остатка или цены чужого предложения; повтор запроса брони уменьшает остаток дважды | Проверка пекарни сотрудника; ограничения в базе; ключ повтора (`AC-03.7`) | ЛР 4А, ЛР 4Б |
| Отказ от совершённого | «Я не получал набор» — «а я выдал» | В брони записаны момент выдачи и сотрудник (И-11); журнал аудита | ЛР 4А (поля), ЛР 7 (журнал) |
| Разглашение | Код выдачи чужой брони; брони другой пекарни; почта покупателей | Код виден только владельцу брони и его пекарне; чужое отвечает как несуществующее; коды и почта не пишутся в журнал (`NFR-05`) | ЛР 3А, ЛР 4Б |
| Отказ в обслуживании | Программа бронирует все наборы и держит их до конца окна; перебор кодов у прилавка; поток регистраций | Не больше 3 наборов и одна бронь на предложение (`AC-03.4`, `AC-03.6`); пауза после трёх неявок (`FR-13`); стойкость кода (`NFR-03`); ограничение частоты входа и брони | ЛР 4Б (простейший вариант), ЛР 7, v1.1 (`FR-13`) |
| Повышение прав | Продавец публикует предложение; покупатель вызывает операции кабинета | Роль и пекарня проверяются **на сервере**, а не скрытием кнопок в клиенте | ЛР 4Б |

### Что предусмотрено и где появится

Кода ещё нет, поэтому здесь не «сделано», а «решено»: меры приняты как правила и появятся вместе с первым кодом.

| Мера | Где появится |
| --- | --- |
| Пароли и ключи не попадают в репозиторий: `.env` исключён (уже в `.gitignore`), в репозитории `.env.example` | ЛР 3А |
| Секреты, почта, адреса и коды выдачи в журнал не пишутся | ЛР 3А |
| Входные данные проверяются моделями `pydantic` на границе | ЛР 3А (настройки), ЛР 3Б и ЛР 4Б (запросы) |
| Пароли — только хеш Argon2id; обновляющие маркеры — только хеш | ЛР 4Б |
| Коды выдачи порождаются криптографическим генератором, не обычным случайным | ЛР 3Б |
| Процесс в контейнере работает от непривилегированного пользователя | ЛР 3А |
| Порты базы и брокера наружу не публикуются | ЛР 4А, ЛР 6А |

### Что отложено и куда

| Что | Куда | Почему не сейчас |
| --- | --- | --- |
| Проверка подлинности и прав | ЛР 4Б | Нужен контракт API |
| Журнал аудита | ЛР 7 | Вместе с наблюдаемостью |
| Ограничение частоты запросов | Простейший вариант — ЛР 4Б (вход и бронь), с хранением в кеше — ЛР 7 | Нужен контракт API; общий счётчик для нескольких экземпляров требует кеша |
| Проверка зависимостей и образа на уязвимости | ЛР 6Б | Вместе с конвейером доставки |
| Подтверждение почты и восстановление пароля | Вне охвата семестра | Нужен почтовый сервер; цена отказа записана в ADR-0004 |
| Полная модель угроз | Вне охвата курса | Введения по STRIDE достаточно для объёма проекта |

## Что осознанно не сделано

| Решение не делать | Причина |
| --- | --- |
| Микросервисы | ADR-0003: бронь и остаток должны меняться в одной транзакции (`NFR-04`); при `C-04` независимость служб ничего не даёт |
| Кеш списка предложений рядом | `NFR-01` при 200 предложениях достигается индексом и запросом по координатам. Кеш показывал бы устаревший остаток — именно то, против чего `AC-02.5` |
| Срабатывание по расписанию для «не забрана» | ADR-0005: вычисление при чтении точнее и переживает простой |
| Вход через VK ID, Яндекс ID или MAX | ADR-0004: нет публичного стенда; бот появляется только в v1.1 |
| Хранение адреса покупателя на сервере | `C-09`: адрес — персональные данные; для `AC-02.7` достаточно запомнить его на устройстве покупателя |
| Оркестрация | `C-05`: практика на Compose |
